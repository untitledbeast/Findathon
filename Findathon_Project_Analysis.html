1. Project Overview

Findathon is a hackathon discovery and aggregation platform — think "Product Hunt meets Google Maps for hackathons". It allows users to discover, search, filter, compare, bookmark, and submit hackathons worldwide. The platform focuses primarily on the Indian hackathon ecosystem but supports global events.

Core Value Proposition: A single unified platform where developers can find hackathons by city, college, technology, prize pool, or natural language queries — with an interactive map, spotlight search (Cmd+K), and personalized recommendations.

4.3 Search Architecture (Critical System)

The search system is one of the most complex parts:

User Query → Intent Parser (NLP) → Search Filters → Repository (Supabase) → Ranking Engine → Results

Components:

  • lib/intent-parser.ts — Natural language parsing. Extracts:
  • Technology tags via synonym expansion (AI, Web3, Cloud, Cybersecurity, etc.)
  • Indian cities (Bangalore, Mumbai, Delhi, Pune, etc.)
  • Online/offline mode
  • Difficulty level (beginner, intermediate, advanced)
  • Prize amount (regex extraction)
  • Timeframe (this weekend, this month)
  • lib/search-ranking.ts — Pure deterministic ranking with score boosts for:
  • Featured (+15) and Verified (+10) hackathons
  • Registration deadline urgency (closing in 3 days: +12)
  • User tag affinity (+8 per matching tag)
  • Proximity boost (+15 for <25km, +10 for <50km, +5 for <100km)
  • lib/discovery-engine.ts — StatelessDiscoveryEngine class that orchestrates the pipeline. Singleton exported as discoveryEngine.
  • lib/search-suggestions.ts — Typeahead search suggestions.
  • lib/search-analytics.ts — Fire-and-forget analytics logging.
  • lib/recent-searches.ts — localStorage-based recent search history.

4.4 Authentication Architecture

  • Provider: Supabase Auth with Google OAuth
  • Context: lib/auth-context.tsx — React context providing user, session, profile, role
  • Auth Callback: app/auth/callback/route.ts
  • Profile: Fetched from profiles table, falls back to Google metadata
  • Roles: user, organizer, moderator, admin
  • Navbar Auth: Dynamically imported with ssr: false to prevent hydration mismatch

9.2 Architectural Issues

  • Mock Data Fallback Everywhere: The SupabaseHackathonRepository silently falls back to MockHackathonRepository on ANY error, empty results, or missing env vars. This masks database connection issues in production.
  • Empty MOCK_HACKATHONS Array: lib/supabase.ts exports MOCK_HACKATHONS: Hackathon[] = [] — the mock fallback returns empty data, making it useless as a fallback.
  • getByIds Performance: StatelessDiscoveryEngine.getByIds() fetches ALL hackathons via discover() then filters by ID in-memory. This is O(N) instead of a targeted query.
  • Browser Client in Server Context: lib/supabase.ts uses createBrowserClient() which may be imported in server-side API routes. Server routes should exclusively use supabase-server.ts.
  • Duplicate Type Systems: types/index.ts defines DTOs using camelCase (HackathonDTO.startDate), while lib/dto.ts defines DTOs using snake_case (HackathonDTO.start_date). This creates confusion about which DTO is canonical.
  • config/env.ts imports z from 'zod': But zod is NOT listed in package.json dependencies. This file would crash at runtime if actually imported.
  • Sitemap uses browser client: app/sitemap.ts imports from @/lib/supabase (browser client) but runs during build time on the server.

9.3 Potential Runtime Bugs

  • Hydration Mismatch Risk: The homepage (app/page.tsx) is 'use client' and uses useRouter but the page uses SSR-unfriendly patterns (e.g., Date objects in renders).
  • mapDtoToHackathon unsafe casting: Homepage function casts unknown DTO shapes to Hackathon type with as unknown as Hackathon, bypassing type safety.
  • Missing Error Boundaries: Individual page sections don't have error boundaries — a single failing section (e.g., recommendations API) could crash the entire homepage.
  • Compare Store Memory: The compare store keeps IDs in memory but doesn't persist across page refreshes or validate that IDs still exist.
  • Race Conditions in Search: The debounced search in UniversalSearch.tsx doesn't cancel previous in-flight requests when a new query is typed.

16. Important Notes for AI Agents

🔴 CAUTION
**Critical Quirks to Know:**
  • Next.js 16: This project uses Next.js 16.2.12 with React 19. API behaviors may differ from Next.js 14/15 training data. Always check node_modules/next/dist/docs/ for current API docs.
  • Dual DTO Systems: There are TWO separate DTO type definitions:
  • types/index.ts → camelCase (startDate, endDate, isOnline)
  • lib/dto.ts → snake_case (start_date, end_date, is_online)

The lib/dto.ts version is the canonical one used by the discovery engine and repositories.

  • Supabase Client Split: Three separate clients:
  • lib/supabase.ts → Browser client (for client components)
  • lib/supabase-server.ts → Server client (for API routes, server components)
  • lib/supabase-admin.ts → Admin/service role client (for privileged operations)
  • Mock Fallback Pattern: The repository silently falls back to mock data on any error. If you see empty results, the DB connection might be broken.
  • INERT Modules: Several modules (event-bus, notification-dispatcher, image-pipeline, feature-flags) exist as typed contracts only. They compile but do nothing at runtime.
  • Zod Dependency Missing: config/env.ts imports zod but it's not in package.json. This file likely crashes at runtime or is never actually imported in the hot path.
